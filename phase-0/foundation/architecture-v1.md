## 1. 最小实用结构

**建议采用模块化单体：一个主要应用部署，内部按业务职责隔开。**例如品牌审核和财务核对可在同一应用，但只有账务模块能生成或调整奖励义务。这样Belcort无需为小试点维护多套独立服务，也给未来课程、商店和联盟留下边界。

建议组件：响应式网页；同一代码库中的业务应用与后台任务；一个支持事务的关系数据库；私有对象存储；邮件通知；托管身份服务和支付适配器。事务指一组记录全部成功或全部不变，防止作品已批准但奖励漏记。后台任务仅负责可靠发送通知、同步支付和核对，不引入独立流处理平台。

具体语言、框架、云、数据库托管、身份商、邮件商和支付商由Belcort在可行性阶段提交对比和报价，当前不指定产品名称或区域。旧[经营模型](../deliverables/research/operating-model.md)中的特定供应商、自聘团队、费率及品牌直付路线是历史情景，不能作为本稿默认或已确认能力。暂不建微服务、开放插件平台、AI风控、社交数据仓库或视频转码系统。

应用读取自身业务记录；社交平台只提供用户提交的链接/人工证据，不成为报酬计算的强依赖。默认不自动抓取任意链接，避免网页抓取能力成为试点前置。若未来增加抓取，要独立评估权限、私网地址阻断和平台许可。

## 2. 领域实体与唯一归属

领域实体是业务中必须有独立身份和历史的对象，例如“作品”和“付款”必须是两条记录。所有金额用币种加最小货币单位整数表示；V1只接受MYR。时间存统一时间点，展示明确马来西亚时区；不以浏览器当地时间裁决截止。

| 模块/负责人角色 | 所拥有实体与关键字段 | 可接受的外部输入；禁止的越界 |
|---|---|---|
| 身份与组织 / Belcort实现、Wringy批准权限 | User、Organization、Membership：user_id、organization_id、role、授权/撤销时间 | 认证结果与邀请；不能因为知道组织ID就获得访问权 |
| 活动与内容 / 产品负责人 | Campaign、RuleVersion、Slot、SubmissionVersion、ReviewDecision：组织、期限、单价、权利文本版本、作品来源、审核人/理由 | 用户提交与品牌决策；不直接编辑银行状态 |
| 奖励与资金核对 / 财务规则负责人 | BudgetAllocation、RewardObligation、Adjustment、PaymentAttempt、PaymentAllocation、Refund、ReconciliationCase：金额、币种、债务人/收款人、合同版本、证据引用 | 最终审核决策、核实的资金事件；只有本模块记账，其他模块不能各造余额 |
| 风险与支持 / Wringy运营 | EligibilityRecord、RiskHold、Case、CaseDecision：对象、原因、权限范围、到期复核、裁决人 | 核验状态与人工证据；风险标记不能自己消灭应付款 |
| 外部连接 / Belcort | ProviderAccountRef、InboundEvent、OutboxTask：提供方、账户映射、唯一事件键、签名验证结果、处理时间/次数 | 验证过的回调或人工导入；不自行判断业务是否应奖励 |
| 共用支持能力 / Belcort | PrivateAsset、Notification、AuditEvent：归属组织/用户、可见范围、校验摘要、保留策略、操作者、关联编号 | 各模块提交安全事件；日志不是业务账本，邮件成功也不是付款成功 |

RewardObligation记录合同债务人、创作者收款身份、最终决策ID、规则版本、原始金额和当前未清偿金额；不能默认债务人就是Wringy。预算记录的是活动奖励承诺容量，与服务商真实资金覆盖分开。PaymentAllocation关联某一笔已证实付款实际清偿了哪笔义务和多少，支持部分付款及退回。服务费发票和收入记录独立于奖励本金；会计确认规则另由财务确认。

所有组织业务实体带organization_id；用户本人奖励记录还校验creator_id。私有文件关联对象而非可猜的公开路径。数据库唯一约束至少包括：同活动/创作者有效名额、同最终作品奖励义务、供应商/事件ID、幂等键作用域。同作品多次版本不会获得多份奖励。

## 3. 模块边界和依赖方向

建议仓库内部目录为 `modules/identity`、`modules/campaigns`、`modules/settlement`、`modules/risk-support`、`adapters`、`shared`；这是未来目录提案，本轮未创建。每模块有规则文件，说明词汇、入口及依赖，根规则文件索引各模块。

- 页面与任务入口调用业务用例；用例可组合活动、资金和风险接口，不直接暴露数据库给前端。
- 活动模块输出“最终决策”及条款快照；资金模块接受经授权的决策和冻结金额，拥有预算检查与奖励记录。
- 风险模块输出具名限制/裁决；资金模块据此暂停或执行调整。风险模块不能直接修改账务表。
- 支付适配器实现业务定义的付款/查单/退款接口；外部字段在此翻译，供应商状态不直接成为页面状态。
- 共用模块只放ID、金额、时钟和审计等基础能力，不放含糊的“通用业务规则”。分析读取受控视图，不能反向写业务记录。
- 模块间通过公开接口；单库事务可跨活动及资金用例协调，仍由各模块写自己的记录。上线前用依赖检查工具阻止跨模块私有导入、循环依赖和绕过资金入口；具体工具待语言选择。

将来B02订单/订阅、B03权益、B07佣金加入时，各自产生交易/履约事实，经统一资金入口建立其义务；权益模块不能把付款按钮当交付成功。只有独立伸缩、安全或团队边界有实测需要才拆服务，不先为12板块建设分布式基础设施。

## 4. 一次最终批准如何可靠发生

1. 服务端校验操作者、当前组织、规则版本、作品版本和预期状态。品牌审核員只能处理被授权活动。
2. 在一个数据库事务中锁定或条件更新名额/预算，确认作品尚未最终批准且额度足够，写ReviewDecision，将预留额度转为奖励义务，并写待发送事件。
3. 同一决策重试返回原结果；竞争操作只有一个成功，失败方重新读当前状态。无记录时不返回成功。
4. 事务提交后后台读取OutboxTask发送通知或安排后续核验。Outbox意为“先把待发消息与业务记录一起保存，再可靠送出”；邮件失败不会回滚已成立义务。
5. 对外content-approved、reward-eligible和paid的定义统一引用PRD“钱的路径与例子”，不另造显示规则。付款是另一个受控动作，需要资金覆盖、收款人资格、无生效暂停、达到约定付款条件以及适用的第二人批准。不能在审核页面按钮内直接触发不可追踪的银行操作。

对应PRD AC-03、05、06、09、16。上述为设计，不是已跑过的实现测试。

## 5. 预算、资金和奖励三份记录怎样核对

必须分清：**承诺容量**（活动最多答应多少）、**资金覆盖**（有何证据说明钱可用于履约）、**实际付款**（钱执行到哪一步）。它们不会天然相等。

### 活动承诺容量

设已批准活动上限为C；可新承诺额度为A；已接受但尚未最终处理的名额额度为R；累计净奖励承诺为O。保持 **C = A + R + O**。O包含已付与未付的有效奖励，不因付款就归零，否则同一预算会被再次承诺。批准作品时R减少、O增加；有效取消/到期释放时R回A；未付款义务有效撤销时以Adjustment减少O并增加A。活动关闭或资金异常时即使A为正也不允许重新招募。

C只由具名预算变更增加/减少；减额不得侵占R和O。C不是服务商账户余额，也不证明实际存款已到。服务费、税和通道费不藏进C。

### 奖励义务

单笔未清偿额 = 原义务金额 + 已批准调整 − 已核实清偿分配 + 已核实退回重新形成的应付。不能小于零；追索作为独立案件/应收，不把用户可提现余额变负来隐藏损失。每个调整保留原记录、原因、证据、批准人和关联案件；不能删账修数。

例：RM100义务已核实支付RM60，则未清偿RM40；随后确认RM60退回，未清偿回到RM100。原支付和退回都保留，不把付款历史改成“从未发生”。供应商内部入账是否构成清偿由合同决定；银行状态仍独立展示。

### 服务商/银行资金覆盖

逐账户、币种和核对期间记录：期初资金 + 已核实入金 − 已核实付款 − 退款 − 费用/扣款 = 期末资金；冻结/限制款与可用款分列，内部转账成对排除重复计算。若服务商数据将可用、冻结和在途分开，先做状态映射再核对，不拿不同口径硬相减。

与PRD一致，服务商路线在活动开放、新名额接受和付款前必须满足：经核实且分配给该活动的可用服务商资金 ≥ 受保护名额金额＋未清偿奖励＋适用费用负债。新名额按加入后的金额原子检查/预留；同一资金不能跨活动重复分配。冻结、限制、未清算或未知资金不计覆盖；在途付款继续占用直到结果核实，避免重复分配。证据过期或不明同样阻断相关操作并转对账。原始入金证明不等于永久资金保证，退款、拒付或冻结后必须重算覆盖。品牌直付备选无法验证托管覆盖时明确标“未预存资金的品牌付款承诺”，逐笔记录债务人和约定到期日，不可显示为托管或“已预存保障”。

三向对账：Wringy义务/指令 ↔ 供应商执行记录 ↔ 银行或收款结果证据。每次真实付款前及活动收尾核对，试点建议每日处理未决差异；无业务日只检查待决记录。保留来源、时间、金额、费用、外部ID和核对者。未知结果、余额不符、超额付款、币种不符进入ReconciliationCase，暂停相关新付款；负责人解决前不以手工改余额消除差异。

## 6. 失败、退款、逆转与追索

| 事件 | 正确动作 | 禁止动作 |
|---|---|---|
| 发起请求超时 | PaymentAttempt记unknown；先按原请求ID查单/对账；保持原幂等键，确认未执行才重试 | 再建一笔或转人工另付 |
| 供应商拒绝且明确未执行 | 保留失败原因和未清偿义务；修正收款条件，批准后用关联的新尝试 | 删除失败记录或取消奖励 |
| 收款账户变更 | 重新核验归属、撤销旧指令资格并双人复核；历史引用不可变 | 付款处理中直接替换原收款人 |
| 回调重复/乱序 | 先验签/来源、查本地去重；不支持倒退的转换转查单；留原始受限证据 | 将晚到processing覆盖confirmed |
| 已确认出款后退回 | 记录returned事件及对应金额，重开未清偿项；核对重复事件 | 继续显示全额已清偿 |
| 未付款奖励因申诉/欺诈裁决取消 | 先暂停；具名裁决批准Adjustment并通知，按合同释放相应容量 | 风险标记直接删义务 |
| 已付奖励被争议 | 保留付款事实，建立追索/损失案件；取得合法依据和批准后另行退款/追回 | 把银行支付“倒放”、自动从其他活动扣钱 |
| 品牌取消/退未使用资金 | 先保留既有名额、待审、争议和未清偿义务所需金额；批准可退额，再独立执行退款 | 将总预算全退或以退款批准代替到账 |
| 品牌拒付/服务商冻结 | 记录资金缺口，暂停新增承诺/相关付款，按合同确定补款与损失承担 | 自动转嫁给已履约创作者或用其他品牌的钱补洞 |

人工备选同样需要PaymentAttempt、证据和独立复核。上线前必须具名指定经办人与另一位独立复核人，确认权限、可投入时间和替补安排；未落实不得上线。没有两位独立可用人员时暂停真实付款，不用两个人工“角色”由同一人点击来伪造分离。

## 支付服务商决策关卡

这里列的是待核查问题，不作现行法规、费率、国家可用性或到账时间结论。研究入口为[马来西亚待验证清单](../research/whop-full/malaysia-readiness.md)、[资金版本研究](../research/cr-v2/money-version.md)；Whop/CR文档仅为流程参考，不能授权Wringy使用相同模式。需在真正选型时查当期官方资料、书面报价和专业意见。

| 关卡 | 所需证据 | 负责人建议/通过条件 |
|---|---|---|
| G1 合同与责任 | Wringy/品牌/创作者/服务商实际法律主体；谁采购、谁欠奖励、谁收款保管、何时清偿、谁承担损失 | 创始人＋当地专业顾问确认书面资金图及合同；仅接入服务商不算通过 |
| G2 可用性与资格 | 马来西亚组织和创作者实际开户、币种/方式、身份核验、收款人数量/类型、金额限制、限制行业 | Belcort取证，Wringy确认业务可接受；营销国家名单不足以通过 |
| G3 完整成本 | 处理、账户、出款、退款、拒付、汇兑、准备金及费用承担方的正式条件 | 财务将成本填入实际报价；不套旧研究固定费率，不把冻结款计可用现金 |
| G4 执行与异常 | 沙盒/获授权试单记录：入金、奖励清偿、出款、失败、延迟、重复回调、退款和对账 | Belcort证明能映射本PRD状态；明确哪些不能在沙盒验证，补实测计划 |
| G5 隐私与退出 | 数据处理角色、存储/跨境、核验资料留存、事件导出、账户关闭及未结款处理 | Wringy专业确认＋Belcort执行方案；有可读历史与未决清单 |
| G6 上线批准 | G1–G5证据、已批准条款、具名运营、端到端验收和回滚结果 | 创始人批准具体资金路线与上线范围；不能以本稿批准推定通过 |

**推荐顺序：**先验证服务商管理资金方案。若资格/责任/费用不可接受，提交品牌直付＋独立核对的人工试点变更，重估信任、欠款、客服成本并获批；第三选项为仅无资金原型。尚未选择任何供应商，未授权申请账户或移动资金。

供应商切换不是一个按钮：停止新指令、核对全部在途/unknown、导出历史及余额、按合同处理未结款和收款人重新核验；新活动才用新路线。旧指令继续由旧服务商查证直到关闭，禁止新旧通道双付。代码中保留provider_id、provider_account_id和外部引用，不把一个供应商状态写死为通用事实。

## 8. 提议的内部接口契约

接口契约是各模块事先约定输入、输出和失败方式。以下是拟议内部接口，不是已存在API，也不是对外开放平台承诺。

| 操作 | 输入与前置条件 | 输出/唯一性 |
|---|---|---|
| AcceptSlot | campaign_id、规则版本、身份、幂等键；活动开放且有容量 | slot_id、条款快照；同活动/创作者仅1个有效名额 |
| SubmitVersion | slot_id、私有资产引用、版本、平台链接（最终阶段） | submission_version_id；保留旧版本，检查归属 |
| DecideSubmission | version_id、expected_state/version、approve/reject/change、理由、操作者 | decision_id；最终批准在同一事务生成obligation_id |
| PlaceHold / ResolveCase | 目标、作用范围、原因、证据、具名批准 | hold/case_id和生效状态；不自动改金额 |
| PreparePayment | obligation_id、amount_minor、currency、收款引用、路线版本 | attempt_id；金额≤未清偿额，暂占付款分配防并发超付 |
| AuthorizePayment | attempt_id、独立复核人、预期版本 | authorized；再检查资格、覆盖和暂停 |
| Send / LookupPayment | attempt_id、稳定外部请求键、金额/币种、收款引用 | 执行状态、证据时间、供应商引用；未知结果显式返回 |
| RecordManualEvidence | attempt_id、凭证、来源、操作者 | evidence_pending；独立核对后才能分配清偿 |
| RequestRefund / RecordAdjustment | 关联义务/入金/案件、金额、原因、授权 | 独立记录；批准与外部执行分离 |
| ReadRewardStatement | 当前用户及组织授权、分页条件 | 原始义务、调整、支付阶段、未清偿额、可解释原因 |

通用规则：服务器生成可信操作者上下文，不接受客户端声称“我是审核员”；幂等键按组织＋操作范围隔离，同键不同参数返回冲突；所有敏感写入带版本检查。预期错误至少包含forbidden、stale_version、insufficient_capacity、payment_ineligible、reconciliation_required、provider_unknown；用户界面翻译成可行动的中文/英文文案，不暴露秘密或其他客户信息。

提议事件包括SubmissionApproved、RewardRecorded、PaymentExecutionObserved、PaymentReturned、RefundObserved、HoldChanged。每个事件带唯一ID、schema_version、组织/对象引用、发生与收到时间、模拟标记和关联请求ID；不在事件总线传播身份证或银行账号。接收回调先验证并保存去重记录，再处理；不支持验签的渠道须使用经批准的查询/导入校验，不信任公开请求。状态不能确认时转人工核对，不猜测终态。

## 9. 数据、安全与运营底线

这些是建设验收要求，未证明现有环境已经做到。

- 所有读写服务端强制用户/组织授权；数据库也约束组织关系。组织A的文件、导出、通知和后台任务不能绕过同一边界。高权限及资金操作启用强身份验证和二次确认；撤销权限对后续敏感操作立即生效。
- 支付/核验敏感资料优先由服务商托管；Wringy只留必要状态、外部ID和证据引用。人工银行凭证限制财务可见、遮盖无关信息；不得在聊天或日志复制完整敏感资料。
- 文件私有、限时访问、上传类型/体积限制及扫描策略在实施规格确定；拒绝可执行文件。日志和审计分离：审计保留谁/何时/为何作何决策，业务历史不能通过普通编辑删除。
- 数据保留由Wringy根据合同及专业确认列对象/目的/期限；目前不编造统一法定年限。账号删除、内容删除与必须保留的交易证据区分；冻结案件保留有依据和复核日。生产前确定删除/导出流程及第三方副本处理。
- 数据流清单记录浏览器、应用、数据库、文件、身份、支付、邮件的存储地区和处理商。区域选择、跨境处理和通知责任待专业确认，不保证马来西亚驻留或宣称自动合规。
- 密钥由受控密钥管理保存，开发/测试/生产分开。生产维护访问须有工单、时限及日志；Belcort成员离岗撤权，不能共用创始人账号。
- 监控重点：unknown付款、对账差异、待发送任务积压、越权尝试、审核超时、接口失败、备份失败。具名接收人和升级路径须在上线前落实；没有全天响应承诺。
