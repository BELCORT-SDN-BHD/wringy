## 主会话实际检查

已通过Codex内置浏览器查看桌面首页与表单。必填空提交聚焦首个错误字段；填入模拟标题和example.com测试邮箱后，模拟失败保留内容并出现重试；重试显示仅本地保存成功。未发送业务数据。以下问题已提出修订要求，只有复核后的条目才算结案。

| Before | After | Why |
| --- | --- | --- |
| 业务控制台把预审、终审、资格、处理和银行当作五条主轴，缺少计量与风险 | 五轴为内容、计量、奖励、付款、风险；预审与银行证据成为对应子状态 | 与领域合同一致，不掩盖断连或开放风险 |
| 禁用保存按钮后焦点落到页面主体，失败后未返回 | 保持busy按钮可聚焦并阻止重复提交，或只在焦点仍丢失时恢复 | 键盘用户能够继续重试，不被迫从页首寻找 |
| 示例通过关键词正则猜组件类别，存在financial匹配ai等风险 | 用103个稳定组件ID做明确映射，专属组合有自己的结构 | 组件名不能决定错误的视觉样例；覆盖要可核验 |
| 状态选择器列出全部状态，却有样例仍显示默认事实 | 对已覆盖状态绘制对应事实；未绘制项明确记作仅契约 | 下拉菜单存在不等于状态视觉已经设计 |
| 目录导航高亮停在前一节 | 高亮按实际阅读位置或当前锚点同步 | 侧栏应帮助定位 |
| 旧规范仍称design-v3为当前唯一token源 | 新源统一为本目录tokens.json；旧文件只保留来源 | 扩展后的语义、警告色与Emil曲线能够统一生效 |

## 独立跨供应商审阅

使用本机Claude Code 2.1.259，关闭工具、配置扩展与会话持久化，只提供domain-states和12个相关组件的封闭文本包。没有提供凭据或真实用户/交易数据。原始结果保存在项目 `.scratch/wringy-foundations/design-system-review/result.json`。这是文字规格审阅，不是运行时安全审计。

主会话接受下列澄清，不把审阅建议直接变成已批准商业政策：

1. payable之后、实际出款之前是否可加风险限制必须说清；保留原义务，实施权力仍属待批准政策。
2. 奖励/风险的unknown首先是观察失败；保留最后事实，不暗示零奖励或没有风险。
3. 付款追加认证阶段可收到提供方确定失败；这不同于超时未知。
4. 确认弹窗是跨模块基础组件；目录的模块关联不能遗漏资金场景。
5. 计量修正影响尚在累积/待结算的奖励时，标为核对中并阻止未核对增量释放，保留旧记录；正式修正算法仍待决定。

审阅未验证真实数据来源、平台接口、服务商准入、生产权限、真实手机或辅助技术。所列缺口不等于这些能力已经实现。
