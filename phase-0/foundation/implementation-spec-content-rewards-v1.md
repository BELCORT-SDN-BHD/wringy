## 1. 一页实施约定

**为谁：** 商家配置活动，创作者提交并申请奖励，运营审核，获授权财务处理付款。**成功：** 同一申请在三角色中可追溯，预算只占用一次，申诉不丢预留，未知付款不会重付。

**证据：** 创办人方向和五项规则已记录；投资人认可为转述的构想认可，非客户付费验证。竞品实测止于可见新账号流程，未证明Wringy数据或支付能力。

**本轮投入范围：** 只完成一份可审阅实施规格，不以公司开发预算裁剪，不开服务、不造应用、不写代码。冻结后可先模拟开发，真实授权和联调在生产开放前完成。

**不做：** 商城课程、通用SDK、七套服务、自建密码系统、钱包、自动化取整定案、供应商采购。**上线后观察：** 付费与复购、申请和申诉结果、账本差异、付款未知及对账耗时，不填虚构目标。

**批准：** 本规格整体待创办人审阅；技术负责人需确认约束和迁移方案，主任务汇总。40项验收均未执行；文档冻结、模拟验收、生产验证三个节点不能合并。

## 2. 已确认技术方向及部署边界

2026-09-15创办人确认[全栈方案](full-stack-proposal-v1.md)，技术选型以该文件及三路审核修正为准：

- 业务前端Next.js＋React＋TypeScript；沿用shadcn/Tailwind设计系统，三语采用next-intl。Vite只保留现有设计系统展示用途，不作为业务前端方案。

## 3. 物理结构草案

PK为主键，FK为外键，U为唯一约束。ID建议UUID，事件时间用带时区时间戳，金额用币种＋`bigint`最小货币单位；原始指标可用精确`numeric`。JSONB仅放规则文案／非金额扩展和提供方元信息，费率、余额、门槛和状态不是JSON金融真相。下表是拟议表，不是迁移文件。

|表|关键列与约束|
|---|---|
|profiles／orgs／org_members|profile.id关联托管auth subject；组织PK；成员PK(org_id,user_id)，角色CHECK；偏好限三种代码|
|admin_scopes|PK(user_id,org_id,capability)，FK成员及组织；review与finance独立，不设隐含全局通行证|
|campaigns|PK id；U(org_id,id)；状态、当前版本、币种、funding_evidence_ref；奖励总额与四类金额CHECK非负，合计等于奖励总额|
|campaign_versions|PK id；U(org_id,campaign_id,id)及版本号；复合FK到活动；费率分子／计量单位、门槛、封顶、日历与跨平台许可列；生效后禁止更新／删除|
|account_connections|PK id；U(user_id,platform,account_id)，U(user_id,id)；账号类型、控制证明、grant范围及令牌安全引用；重复账号归属进入冲突复核，不自动授给另一人|
|submissions|PK id；org_id、campaign_id、creator_id、connection_id、platform、post_id、version_id、accepted_at、baseline_snapshot_id；U(campaign_id,platform,post_id)；复合FK保证活动／版本同组织及connection属于本人|
|metric_snapshots|PK id；复合FK(org_id,submission_id)；原指标名、nullable值、missing_reason、来源覆盖起止、source_time、observed_at、fixture/live；CHECK值和缺失理由二选一|
|claims|PK id；复合FK到投稿；snapshot_id须属于同投稿；规则版本、冻结截止、金额、valid_at、queue_seq、状态；U(campaign_id,queue_seq)，部分唯一索引保证每视频一个未结申请|
|request_dedup|PK(actor_id,route,request_key)；组织、request_hash、result_ref／stored_response；同键不同请求拒绝，同请求返回原结果|
|reviews／appeals|各自PK；复合FK到申请；reviews区分内容／计量结论及证据；appeals含申请人、截止、受理与最终结论，未决不得释放|
|ledger_entries|PK id；复合FK到活动及相关申请；from_bucket、to_bucket、amount_minor、currency、reason、command_id；CHECK正额且不同分类；U(command_id,entry_no)，只追加|
|obligations|PK id；U(org_id,claim_id)，复合FK申请；金额币种、settlement_confirmed_at、settlement_evidence_ref；不可由提供方success直接填结清时间|
|payout_attempts|PK id；复合FK义务；provider、provider_ref、request_key、stage、pending/success/failure/unknown、事件引用；同义务未解决尝试部分唯一；提供方引用与请求键唯一|
|outbox／audit|outbox事件ID唯一、类型版本、关联记录、处理状态、next_attempt_at；audit只追加操作者、组织、对象、动作及前后引用，不记录令牌|

所有租户子表同时存组织及父ID，父记录提供对应复合唯一键，FK必须引用这组键，不能只验证随机ID存在。账号连接是创作者私有记录，商家只经投稿取得必要证明。索引至少覆盖成员查询、活动状态、投稿归属、申请活动序列／待审状态、未决申诉、未解决付款与到期任务；不要为所有字段盲目建索引。

账本一致性不是跨行CHECK可自动保证：金额迁移必须经唯一受限写入路径，在同一事务更新活动分类汇总并追加分录。禁止其他模块更新汇总，恢复与对账验证汇总等于分录。冻结版本及追加表由数据库权限／触发约束落实，不能只写注释。模拟与live记录分离环境并校验来源，不能从fixture生成真实义务。

## 4. 关键事务与失败恢复

申请前在事务外获取快照，不持数据库锁等待网络。事务按固定顺序锁活动行再锁投稿行；复核组织、版本、快照所属与有效性、单条剩余、去重键及待处理申请。获得锁后由数据库实际时钟记录valid_at，并分配活动内递增queue_seq；不用事务开始时间或客户端时间。这样排队与预留同一序列，不按审核完成先后分配。

同一事务冻结全量可申请增量、迁移可分配到预留、追加账本与outbox、保存重复请求结果。崩溃回滚全部，重试复用请求键。快照变更不能改变已冻结金额；统计回落进入复核。取整按2026-09-15已批准累计取整规则执行；实现与测试仍未完成。

部分金额先出不占钱的提示，明确同意后重核；报价改变须重新明确同意；完整验证接受时取得有效排序，按已批准默认规则执行。候补已确认不占钱，通知后重提取得新优先级；通知不是预留。最终拒绝释放须检查申诉已结束，不能定时任务到点盲目释放。

确认奖励将预留转确认未付并建立唯一义务。启动付款时锁义务、检查未解决尝试，先记录尝试和outbox再异步调用；网络超时记unknown，查询原尝试，不新建付款。success仅表示指定提供方阶段成功；保持“提供方账户已发放”与“银行到账”可分别记录，结清采用已批准提供方账户资金可用口径，真实路径验证前不开放真实结清。余额仍保持确认未付直至结算证据达到已批准标准。

回调适配器校验签名与事件ID，重复事件不重复生效；乱序旧pending不覆盖成功。审计和状态更新同事务，冲突对账。恢复是停发、核查原义务和尝试，不靠回滚数据库撤销已发生的外部资金转移。

## 5. REST接口草案

所有业务接口先验证主体与组织；变更携带请求键，版本冲突返回409；输入错误400、未认证401、无权限403、资格或能力不就绪422、限流429、暂不可用503。响应分清fixture与live、数据时间及业务状态，不只返回success布尔值。

|方法与路径（/api/v1）|角色／输入|结果与关键失败|
|---|---|---|
|GET/PATCH /me|本人；语言／可选资料|偏好与保存状态；不改其他人资料|
|GET /campaigns；GET /campaigns/:id|本人可见范围|列表／活动规则；私密组织内容不泄露|
|POST /orgs/:org/campaigns|商家；基本资料|草稿ID；组织权限失败|
|POST /campaigns/:id/versions|商家；规则及基版本|新不可变版本；旧版本冲突409|
|POST /campaigns/:id/publish 或 /pause|商家授权；版本／就绪引用|活动状态；缺资金或数据条件422；pause不清债|
|GET /connections；POST /submissions|创作者；活动、connection、URL、规则版本|资格或投稿／待基线；归属、重复与不支持错误|
|GET /submissions/:id|有权主体|基线、快照、窗口、可申请及状态|
|POST /submissions/:id/claims|本人；快照、请求键|全部增量申请／部分提示／候补；单待处理冲突|
|POST /claims/partial-consents|本人；提示引用与明确同意|重核结果；具体报价模型和排序待定，不视为冻结端点|
|GET /claims；POST /claims/:id/reviews|授权商家内容审／运营计量审；结论证据|各项独立状态；越权或版本冲突|
|POST /claims/:id/appeals；POST /appeals/:id/resolve|本人申诉／限定复审员；理由证据|受理／结论，保留预留直至最终处理|
|POST /obligations/:id/payout-attempts|财务；请求键|尝试ID；存在未知或pending拒绝新尝试|
|POST /payout-attempts/:id/reconcile|财务；原尝试引用|可核对结果；不猜测提供方状态|
|GET /campaigns/:id/records|商家及限定运营；筛选|投稿、账本、付款必要视图，个人敏感字段裁剪|

社交授权与支付回调由各官方SDK／适配器契约确定，不在此虚构通用OAuth回调。后台基线采集、候补通知、48小时升级、申诉到期复核用同一PostgreSQL outbox作业，支持重试和重复消费；活跃申诉无自动过期。外部接口字段与失败样本见[内部契约](external-interface-contracts-v1.md)。

依据[2026-09-14时间规则核查](../research/content-rewards-timing-benchmark-2026-09-14.md)，Clipping、Whop Program和独立CR的计量、周期及付款规则不同，没有据此认定统一申请期限。本补充已由用户于2026-09-14回复“ok”单独批准，唯一规则源为[默认配置申请期限](campaign-defaults-v1.md#申请期限2026-09-14已批准)。它补足D04原期限缺口，该日期仅批准期限；六项规则已于2026-09-15另行批准，完整规格仍未冻结。

已批准保留接受链接起7天计量及达标主动申请；计量结束后默认再给7个日历日申请宽限。商家可在发布前设置正的明确天数，不追溯更改。此7天现为已批准产品默认，不是竞品标准。

若平台数据故障或同视频既有待审／申诉阻挡新增申请，受影响者在最终计量数据可用且阻挡解除后仍有完整7天（商家另设时使用公布天数）。原因、解除时间及具体新deadline留记录并通知。窗口结束不延长计量，不改变计酬快照口径、不加入窗口外观看，不补历史排队时间，也不保证预算。

例：Asia/Kuala_Lumpur的9月1日12:00接受，9月8日12:00计量停止，正常9月15日12:00申请截止。已确认奖励和及时提交的申请不会因截止清除。申请期限验收要求：分别检查正常截止、迟到数据恢复、同视频待审阻挡解除，以及到期仍保留已提交申请；均未执行。
