| R4 | **One audit writer, two entry points (`apps/api/src/audit.ts`).** `writeAudit(client, entry)` runs on the command's own transaction client and commits with the change (an allowed outcome and its audit row are one transaction). `auditDenial(pool, entry)` opens its **own short transaction on a fresh pool client** after the business transaction has rolled back (IT4): the row is written from the route's catch block, never on the client whose transaction is being discarded, or every denial row would vanish with the rollback. A failure to write the denial row is logged as a reason word at `warn` and the refusal is still answered: the audit is never a way to fail open, and never a way to turn a 403 into a 500. `AuditEntry` is a closed type: `{ actorKind, actorUserId, actorLabel?, contextOrgId?, action: AuditAction, targetType?: 'org' \| 'org_member' \| 'org_invitation' \| 'admin_scope' \| 'platform_grant' \| 'sign_in_allowlist', targetId?, outcome, denialCode?: ErrorCode, reason?: string, summary?: AuditSummary, requestId, sessionRef }`; `AuditSummary` allows only `before`/`after` objects with the keys `role`, `status`, `capability`, `name` — a unit test asserts an entry with `email`, `token` or an unknown key is refused by the type-level guard `assertSummaryShape`. **Actions** (stable strings, the `action` CHECK enforces the `noun.verb` shape): `org.create`, `org.rename`, `org.read`, `invitation.create`, `invitation.revoke`, `invitation.accept`, `invitation.preview`, `member.role_change`, `member.remove`, `member.leave`, `capability.grant`, `capability.revoke`, `allowlist.add`, `allowlist.remove`. Allowed **reads** are not audited (the org page would flood the table); every **denial** is, reads and commands alike, with `denial_code` = the HTTP error code and `reason` = the internal reason word (`not_a_member`, `org_unknown`, `member_role_required`, `last_admin`, `email_mismatch`, …). A body or header naming an org is ignored, and a test sends `{ orgId: <other org> }` in the body of a command to prove the path decides (the M2-02 "X-User-Id / body orgId are never read" rule, restated for paths: the path is a *claim* the server re-authorises, never an authority). **Reads** (`GET /orgs/:orgId`) call `readActiveMembership(client, orgId, userId)` on a pooled client at the start of the handler; no row (unknown org, never a member, removed) → 403 `org.forbidden` + a denial audit row with reason `not_a_member` or `org_unknown` — the same answer for both, so an outsider learns nothing about which org ids exist. **Commands** run inside `withTransaction`, in this order: (1) `requireLiveSession` on the transaction client (M2-02 R2, as the probe does); (2) `lockProfileStatusForShare` (a disabled account is refused before any work, M2-02 R6); (3) `lockActiveMembershipForShare(client, orgId, userId)` — `SELECT … FROM app.org_members WHERE org_id = $1 AND user_id = $2 AND status = 'active' FOR SHARE`, so a concurrent removal or demotion serialises against the command; (4) the role check (`admin` required for rename, invite, revoke, role change, remove); (5) for anything that can change the set of active admins (role change, remove, leave, accept-as-admin), `SELECT id FROM app.orgs WHERE id = $1 FOR UPDATE` — the org row is the mutex the last-admin rule holds (§3.2), possible because `wringy_api` holds `UPDATE (name)` on `app.orgs`; then `SELECT count(*) … WHERE role = 'admin' AND status = 'active'`; (6) the write and `writeAudit`. ## 3. Route table and request flow (as designed)

API (all behind `app.authenticate`, `private, no-store`, `Vary: Authorization`; `[cmd]` = liveness + profile lock inside one transaction, audit on success; every denial audited):

| Route | Who | Answer |
|---|---|---|
| `GET /me/workspaces` | signed in | personal context, active memberships, grants (R10) |
| `POST /orgs` `{ name }` [cmd] | signed in | 201 org + admin membership (`org_created`) |
| `GET /orgs/:orgId` | active member | org, members (display name, role, since), own role; admins also pending invitations |
| `POST /orgs/:orgId/rename` `{ name }` [cmd] | admin | 200 |
| `POST /orgs/:orgId/invitations` `{ email, role }` [cmd] | admin | 201 invitation + token (once) |
| `POST /orgs/:orgId/invitations/:invitationId/revoke` [cmd] | admin | 200 |
| `POST /invitations/preview` `{ token }` | signed in | org name, role, expiry, state |
| `POST /invitations/accept` `{ token }` [cmd] | the invitee (verified address) | 200 org + membership |
| `POST /orgs/:orgId/members/:userId/role` `{ role }` [cmd] | admin | 200; 409 `org.last_admin` |
| `POST /orgs/:orgId/members/:userId/remove` [cmd] | admin, not self | 200 |
| `POST /orgs/:orgId/leave` [cmd] | active member | 200; 409 `org.last_admin` |
| `POST /orgs/:orgId/capabilities` | anyone | 403, audited (R18) |

Flow of the dual-role walk: Alice signs in → `/internal` shows no workspace but the personal one → creates "Alice Studio" → `POST /internal/orgs/create` → API `POST /orgs` (liveness, profile, insert org `live`, insert admin membership, audit `org.create`) → 303 `/internal/orgs/<A>?outcome=created`. Bob signs in on a second device, creates "Bob Retail", invites `alice@example.test` as member → 303 to the invitation page with the link → hands it over (in the test: read from the page). Alice opens the link → the proxy sends her to sign in with `next` = the accept URL (or straight to the page when signed in) → preview → Accept → `POST /invitations/accept` (token from the body; email match; membership upsert; audit) → 303 `/internal/orgs/<B>?outcome=joined`. `/internal` now lists two workspaces; each is a link — switching is navigation, nothing is audited. Carol opens `/internal/orgs/<A>` → the page's `GET /orgs/<A>` answers 403 `org.forbidden` → `org-forbidden` state; `app.audit_log` holds `{ actor_user_id: carol, context_org_id: A, action: 'org.read', outcome: 'denied', denial_code: 'org.forbidden', reason: 'not_a_member', request_id, session_ref }`.
