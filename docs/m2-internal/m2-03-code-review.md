# M2-03 kickoff code review — organisations, memberships, capabilities and the audit log (开工代码评审记录)

Ticket [M2-03 / #26](https://github.com/BELCORT-SDN-BHD/wringy/issues/26). Design contract:
[kickoff-package.md](kickoff-package.md) §3.1–3.6 (identity and organisation boundary), §8.11, rulings D1–D12 (§9.1),
technical choices IT1–IT4; the M2-02 record [m2-02-code-review.md](m2-02-code-review.md) for everything this ticket

`m2-spec.md` L41): file locations, names, the exact schema and grants, the route table, the audit contract, the web
surface and the evidence plan. Nothing here changes a business rule or a founder ruling; every departure from the
kickoff *text* is listed in §5 with its reason.

Revision 1 (2026-09-26): the orchestrator's draft after the Understand pass (six readers over `packages/db`,
`apps/api` + `packages/contracts`, the internal web build, the internal Playwright harness, the repository checks and
evidence documents, and the M1 permission model) and a completeness critic.

Revision 2 (2026-09-26): four independent critics attacked revision 1 — security and privilege; PostgreSQL mechanics
(the DDL and the lock order were **executed on a scratch PostgreSQL 17.10 cluster** built from the repository's
embedded binaries); testability and spec conformance; stack mechanics against the installed `fastify` 5.12.5,
`@fastify/type-provider-zod` 1.0.0, `zod` 4.6.5, `next` 16.3.5, `pg` 8.23.0 and `playwright` 1.63.0 (the Next
segment rule was reproduced with a real build). 65 findings; every blocker and major is folded in and marked
**(rev 2)**, the minors likewise where they change a decision. Two findings changed the shape of the design: the
command lock order of revision 1 **deadlocked** under ordinary concurrent admin actions (reproduced: `40P01` after
about one second), and the recycled-address risk is **worse** than revision 1 said, because Supabase links a new
identity carrying a known address to the *existing* user id (§1, R16).

Revision 3 (2026-09-27): the adversarial review of the integrated tree (`b4d6054..58ea595`; authorisation,
invitations, audit, PostgreSQL, web, spec and test lenses, every finding put to three independent refuters) and
the fix wave that followed it. Where a finding changed a decision, or the build departed from this record for a
reason the record must carry, the row is amended in place and marked **(rev 3)**; the build's departures are
listed one by one in [acceptance-record.md](acceptance-record.md) §M2-AC03 "Build deviations from the design
record".

## 3. Route table and request flow (as designed)

API (all behind `app.authenticate`, `private, no-store`, `Vary: Authorization`; `[cmd]` = liveness + profile lock + the R5 lock order inside one transaction, audit on success; every authorisation refusal audited):

| Route | Who | Answer |
|---|---|---|
| `GET /me/workspaces` | signed in | personal context, active memberships, grants (R10) |
| `POST /orgs` `{ name }` [cmd] | signed in | 201 org + admin membership (`org_created`) |
| `GET /orgs/:orgId` | active member | org, members (display name, role, since), own role; admins also pending invitations |
| `POST /orgs/:orgId/rename` `{ name }` [cmd] | admin | 200 |
| `POST /orgs/:orgId/invitations` `{ email, role }` [cmd] | admin | 201 invitation + token (once) |
| `POST /orgs/:orgId/invitations/:invitationId/revoke` [cmd] | admin | 200 |
| `POST /invitations/preview` `{ token }` | signed in | to the addressed person: org name, role, expiry, state; otherwise `email_mismatch` only |
| `POST /invitations/accept` `{ token }` [cmd] | the invitee (verified address) | 200 org + membership |
| `POST /orgs/:orgId/members/:userId/role` `{ role }` [cmd] | admin | 200; 409 `org.last_admin` |
| `POST /orgs/:orgId/members/:userId/remove` [cmd] | admin, not self | 200 |
| `POST /orgs/:orgId/leave` [cmd] | active member | 200; 409 `org.last_admin` |
| `POST /orgs/:orgId/capabilities` (params only) | anyone | 403, audited (R18) |
