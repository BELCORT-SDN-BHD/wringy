request-key header to an API that ignores it was a layer nobody asked for, so only the field and its proof remain.

departure changed a decision, the row is amended in place and marked **(rev 3)**; §5 gains the rows marked
**(rev 3)**. The largest changes: (1) **the API decides the account, the page that posted decides the
fallback** (W7, refining W5's "the page that posted decides") — with a session cookie in the jar, a choice
made on any page is saved to the account of the session the API accepts; on the sign-in or not-found page,
which render without a session check, the page switches through the guest cookie, and a refusal or failure
there makes the choice the guest's, carried only by the sign-in that follows. W5 had made every choice there
the guest's, so that it never reached the account whose session cookie arrived, which on a shared device can
be somebody else's (the W4 blocker); that also left a signed-in person's own choice there unsaved, and the
next internal page showed the old account value with no notice (the Spec axis, S1). W7 accepts a choice made

would be (R4; known-issues §M2-04); (2) the carry survives the callback's retryable exits and is spent once
the API has answered for a person (R6); (3) the header switcher switches on submit, not on change, and the
Language card's Save switches in place (R5); (4) a language outcome in the URL is consumed by the next
in-place switch (R5); (5) the unsaved choice carries the instant it was made and decides only while the
account holds nothing newer, so a spent one cannot come back over a newer choice made elsewhere (R3; W7, the
native review's first minor); (6) the proxy and the language handler read one routing module and one
session-cookie test, and R11 names every web file the build added (R11; W7, the Standards axis T1, T4 and T7).

## 2. Decisions

| ID | Decision | Why |
|---|---|---|
| R1 (rev 2) | **Two migrations, one object each.** `0017_profiles_locale_pair_check.sql`: `ALTER TABLE app.profiles ADD CONSTRAINT profiles_locale_pref_pair_check CHECK ((locale_pref IS NULL) = (locale_pref_set_at IS NULL))` — the pair *is* the explicit flag (§5), so the table pins it as `0016` pins `audit_log_denial_code_check`; Down: `DROP CONSTRAINT`. **(rev 3)** `SELECT count(*) FROM app.profiles WHERE (locale_pref IS NULL) <> (locale_pref_set_at IS NULL)` had nothing to run on and was not run: no deployed application database exists yet (the dev and staging Supabase projects hold only Auth, and until M2-09 the application database is a local or test cluster), and every local-cluster profile row was created with both columns NULL (`0008` gives them no default, `0010` kept them out of the runtime role's reach, and nothing else writes them), so the count is 0 by construction; a half-set row would make the ALTER refuse with 23514 and stop the migration, because the CHECK is not added `NOT VALID` (acceptance record, Build deviations W3 3; `0017`'s header says so since `47d8f31`, W5 postgres-2). `0018_profiles_locale_grants.sql`: `GRANT UPDATE (locale_pref, locale_pref_set_at) ON app.profiles TO wringy_api`; Down: the matching `REVOKE`. `EXPECTED_MIGRATION_HEAD = '0018_profiles_locale_grants'`. No INSERT on the two columns, no DELETE, `status` stays ungranted (D12). Manifest: `'app.profiles.locale_pref': ['UPDATE']`, `'app.profiles.locale_pref_set_at': ['UPDATE']`; the comments at `grant-manifest.ts` L66–L71 and L108–L112 name `0018`. The Up texts never say `public.`, `PUBLIC`, `anon`, `authenticated`, `service_role`, `LOGIN` or `PASSWORD` (the word-ban test passed on the critic's draft). **Coverage of the Downs, stated correctly:** the at-`0010` comparison in `migrations.int.test.ts` (L201) reverts every migration newer than `0010` and compares `attacl` and `pg_constraint`, so it catches an incomplete `0017` or `0018` Down; its title becomes "M2-AC01/2 reverting every migration after 0010 (0011–0018) leaves exactly the catalog of a database migrated only to 0010" and its list gains the two; and a **generic row** is added so the newest migration's Down is always checked without further edits: "M2-AC01/2 reverting the newest migration leaves exactly the catalog of a database migrated to the one before it" (a fourth database migrated to `all.length - 1`, `prev = catalogSnapshot`; then on the main database `down 1` → equals `prev`; up → equals the snapshot before). The whole-chain fixed point (L180) is **not** what covers a profiles column grant (`0008`'s Down drops the table); `0010`'s own Down has no coverage and is recorded in known-issues, not fixed (it is applied everywhere and never edited) | kickoff §3.2; M2-02 R6 rev 3; `0010` and `0016` as precedents; PG-3, PG-6, PG-7 |
| R2 (rev 2) | **One API command, `POST /me/locale { locale }`, answering `200 { profile }`; `profileSchema` gains `localePref` and `localePrefSetAt`.** Contracts (`packages/contracts/src/identity.ts`): `LOCALES = ['en-MY','ms-MY','zh-Hans-MY']`, `localeSchema = z.enum(LOCALES)`, `setLocaleBodySchema = z.object({ locale: localeSchema })`, `setLocaleResponseSchema = z.object({ profile: profileSchema })`; `profileSchema` adds `localePref: localeSchema.nullable()` and `localePrefSetAt: instantSchema.nullable()` — so `GET /me`, `POST /identity/sign-in` and the command all answer them.
