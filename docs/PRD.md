# Wringy 产品蓝图

Wringy 让商家把内容推广计划变成规则清楚的奖励活动，让内容创作者凭可核验的合格观看申请奖励，并让运营将审核、申诉与付款处理到底。首发从 Content Rewards 完成这条业务链，长期向覆盖更多创作者商业活动的平台发展。

本文是长期维护的产品入口；阶段交付与验收见 [specs](planning/README.md)，技术边界见 [Architecture](ARCHITECTURE.md)。当前实现只到 M1：三端交互原型（`apps/web`，身份、时钟、计量、通知与付款全部显式模拟）已建成，P01–P11 执行通过，并于 2026-09-23 经创办人验收；真实身份、可保存数据、真实交易与产品验收仍未证明。依据：[M1 验收记录](m1-prototype/acceptance-record.md)、[创办人验收 #9](https://github.com/BELCORT-SDN-BHD/wringy/issues/9)、[原型应用说明](../apps/web/README.md)、[已知限制](m1-prototype/known-issues.md)。

## 1. 定位、愿景与证据

商家决定自己的预算、目标与活动条件；平台提供默认配置和不可绕过的核验、预算及重复保护。创作者应在参与前知道怎样获得奖励，参与后知道观看数据、可申请金额、审核结论和款项究竟到哪一步。价值假设是：让商家更容易持续购买可核验的内容传播成果，让创作者获得可理解、可追溯的赚钱机会。

首发推广市场为马来西亚，基础面向国际用户，跨国收付款保留为目标；实际开放国家、平台与付款方式取决于验证结果。经营主体是待明确身份的马来西亚独立公司，不能用 Belcort 代替。首版单币种已确认，MYR（RM）是沿用规则的显式假设，真实资金接入前仍需确认。[创办人输入](../phase-0/founder-inputs.md) · [全栈方向](../phase-0/foundation/full-stack-proposal-v1.md)。

长期承接完整 Whop 式创作者商业平台的愿景，包括店铺、课程及创作者工具等；本轮只建设 Content Rewards，其他板块需后续范围决定和 specs。当前开发不以历史 RM50,000 研发预算裁剪范围；历史融资材料、15% 示例费率、2–4 个月阶段目标不能变成实施工期、正式价格或增长承诺。[最新预算与范围决定](../phase-0/founder-inputs.md) · [Wayfinder 结案地图](../.scratch/wringy-foundations/map.md)。

已有依据是创办人选择、公开机制研究及参考产品的新账号可见流程。付费需求、用户细分和复购仍待真实试点验证；投资人认可的转述、研究或演示不能替代客户证据。[研究边界](../phase-0/research/clipping-deep-v2/browser/onboarding-findings.md) · [试运营规格](planning/specs/m5-spec.md)。

## 2. 优先用户与问题

| 用户 | 场景与需要解决的问题 | 必须获得的结果 |
|---|---|---|
| 商家／投放方及其团队 | 配置活动、约束支出、审核投稿；需要知道哪些成果可计奖、预算占用在哪、还有什么待处理 | 发布清楚规则，按本组织范围管理活动，看懂效果、费用与未清义务 |
| 内容创作者 | 发现活动、外部发布、提交链接并申请奖励；需要区分观看估计、预留、确认与发放 | 知道资格、可申请增量与截止，收到可解释的拒绝及申诉路径，查询付款进度 |
| 运营与获授权财务 | 核验内容／计量，处理申诉、数据中断、任务失败与付款未知 | 依据原规则和证据完成处置，异常有负责人、操作可追溯且不重复付款 |

这些问题是规划要验证的产品假设；首批商家行业、用户目前的替代办法、问题频率、付费意愿及支持成本尚缺直接证据，由 M5 实际参与和复盘补齐，不编造用户访谈。领域用语沿用 [CONTEXT](../CONTEXT.md)，页面与场景细节见 [三角色流程](../phase-0/foundation/three-role-flows-v1.md)。

## 3. 核心体验与旅程

| 环节 | 用户行为与可见结果 | 必须成立的体验 |
|---|---|---|
| 发现与进入 | 手机或电脑打开公开目录／分享链接，先看条件，参与时登录 | 公开浏览无需登录；只提供 Google 登录；区分官网、公开活动与工作台 |
| 身份与工作区 | 选择语言，以同一账号作为创作者，或创建／加入商家组织 | 明确本人／组织上下文；运营、管理员、财务权限另行授予 |
| 商家准备活动 | 配置规则、素材来源与权利、预算及期限，预览并发布 | 条件可达成；数据和资金未就绪时保留草稿，不假称已备款 |
| 创作者投稿 | 核验适用账号与资格，外部发布后提交 URL | 无素材／成品视频上传；稳定发布 ID 去重，有可信基线才接受并开始计量 |
| 观察与申请 | 查看数据及更新时间，达标后申请全部新增可用奖励 | 估计不等于承诺；只计适用窗口内合格增量，冻结依据并按服务端有效时间预留 |
| 审核与申诉 | 商家核内容，运营核计量与风险；被拒绝者可申诉 | 两项通过才确认；理由可理解，申诉中的相关预留继续保留 |
| 发放与核对 | 财务对确认义务发起付款，三方查看处理状态 | 未知先核对原交易；款项到创作者收款账户且可用才记已发放，银行到账另记证据 |
| 收尾与复购 | 完成计量和案件，核对未清款与可退余额，查看报告 | 结案不抹除义务；真实结果用于决定再投放、修复或扩大开放 |

主流程及异常来自 [产品行为与 A01–A40](../phase-0/foundation/prd-content-rewards-v2.md)、[P01–P11 原型验收](../phase-0/foundation/milestones/prototype-spec-v1.md)；本文不复制验收行。

三端共用 [设计系统 v2](../phase-0/foundation/design-system-v2/README.md)：Linear 信息组织、官方 shadcn 组件、Wringy 配色，按任务与权限区分导航。手机与电脑网页均须完成关键操作；具体视口、键盘及动效检查留在原型 spec。

语言为 English、Bahasa Melayu、简体中文（`en-MY`／`ms-MY`／`zh-Hans-MY`）。询问偏好、允许跳过及后改，明确偏好优先；切换语言保留输入，不重发动作，也不改变金额、规则与时区。活动时钟明确显示 Asia/Kuala_Lumpur。[本地化规范](../phase-0/foundation/localization-v1.md)。

邮件与持久化站内通知来自同一业务事件；邮件失败不丢业务事实。外部数据暂缺时保留最后可信状态、时间及原因；运营看到待处理队列与受控操作，其他用户只见本人有权查看的业务状态。[通知与运营要求](../phase-0/foundation/full-stack-proposal-v1.md)。

## 4. 不可丢失的产品规则

具体数值与算法的唯一维护源是 [活动默认规则](../phase-0/foundation/campaign-defaults-v1.md)，可配置范围见 [活动配置表](../phase-0/foundation/campaign-configuration-v1.md)。商家可在发布前调整允许的条件；反作弊、授权核查、禁止重复计酬、预算一致性与审计不能关闭。保存参与时规则版本，不用后来规则追溯拒付。奖励池、平台服务费和支付手续费分列，奖励池不是平台收入，配置金额也不证明已经备款。

- 投稿不等于申请，观看估计不等于预留。基线前和计量终点后的观看不计奖；缺失数据不等于零或作弊，受众资格不等于实际观看地区证明。
- 累计精确奖励先封顶、向下取整到分，再扣互斥占用；每次只申请满足最低条件的新增金额。同视频一个待处理申请，分次申请不重置封顶。
- 全额申请通过完整核验才取得有效次序并预留。部分报价不占额、不占队列，须本人确认确切金额及版本，变化后重新确认。候补无付款保证，额度恢复后重提取得新次序。
- 内容、计量、申请、付款分开记录状态。审核超时升级，不自动通过；拒绝待申诉或活跃申诉保留相关预留，最终拒绝才释放。
- 停止收稿、计量结束、申请截止、内容保留和付款完成是不同时间点。受数据故障或同视频案件阻挡的申请按公布宽限延展，不能延长计奖窗口、补旧优先级或承诺预算。
- 内容保留覆盖已公布期限、适用申请截止、已有案件和确认款发放中最晚的终点；不存在的案件或款项不制造额外等待。
- 付款未知仍是未清义务，不得重复发放。低于门槛的未确认尾额按既有规则提前披露，不得扣除确认奖励；结案、退款和争议不能静默抹账。
- 跨平台独立计奖须商家明确允许。同平台发布 ID 默认不得跨活动重复计奖；原活动最终拒绝后重提仍须满足新规则和权利要求，不迁移旧观看或资格。

预算始终区分 **可分配／预留／确认未付／已付**。同一奖励从预留转应付再转已付是分类迁移，不能再次扣同一笔预算。详细约束与 D01–D06 测试输入见 [实施规格](../phase-0/foundation/implementation-spec-content-rewards-v1.md)；实现由 [Architecture](ARCHITECTURE.md) 的事务与账本边界承担。

## 6. 成功标准与指标

产品成立首先要求三方能独立完成同一活动，理解同一规则、金额与状态；业务成立需要真实付费和持续参与证据。原型观察独立完成情况、犹豫点、误认估计或付款的次数、返回修改活动的原因，不把模拟成交计为商业成功。[M1 观察要求](../phase-0/foundation/milestones/prototype-spec-v1.md)。

以下保留 [M5 Success Measures](planning/specs/m5-spec.md#success-measures) 和 [产品观察项](../phase-0/foundation/prd-content-rewards-v2.md)，未另加数字目标：

| 指标 | 当前口径／记录要求 |
|---|---|
| 活跃商家、付费商家 | 活跃行为待试运营定义；付费商家必须有真实资金证据，邀请／浏览不算付费 |
| 商家复购率 | 观察期内再次付费商家 ÷ 有复购观察机会的付费商家 |
| 有效投稿与有效申请率 | 记录有效投稿及判定来源；有效申请率＝有效受理申请 ÷ 去重提交申请 |
| 审核／申诉处理与改判 | 记录处理时间、拒绝原因；改判率＝改判数 ÷ 已结申诉数 |
| 预留利用 | 已确认奖励 ÷ 已终局处理预留额；不混入未终局案件 |
| 付款与运行异常 | 付款 unknown 数量／年龄、对账耗时、账本差异、任务积压及恢复耗时 |
| 用户与运营成本 | 用户卡点、支持／处理工时，以及每笔未清款或案件的负责人和下一动作 |

每项记录时间窗、来源、分子／分母及样本限制；零分母记不适用。试点参与者、增长／收入目标及扩大条件尚未确定；扩大开放须依据真实结果作出明确决定。

工程指标另列：已接受的压力测试假设是 **1 万注册创作者、每日 1,000 投稿、数百人同时操作**。300 活跃用户、至少 30 天投稿种子数据、常规非第三方 API p95≤500ms、正常连接下已提交站内状态 5 秒内可见仍是 [量化提案](../phase-0/foundation/full-stack-proposal-v1.md)，未测试、非服务承诺。恢复和响应目标待定，在 Architecture 与 M5 spec 落实，不能由蓝图将假设升级为通过。
