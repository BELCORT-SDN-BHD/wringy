# 用户登录后能跨浏览器保存活动与投稿 (M2-SPEC)

## Problem Statement

原型仅保存在浏览器，商家和创作者无法可靠协作；模拟角色也不能保障其他组织的数据不被读取。

**For whom:** 商家、内容创作者及被授予相应范围的运营/财务人员；当前产品仅Content Rewards。

**Evidence:** [创办人输入](../../../phase-0/founder-inputs.md)及当前批准规则支持范围；公开机制研究和投资人认可不是独立客户付费/复购证据。实际用户与运行证据须在本阶段或试运营产生，本稿不虚构访谈、测试或完成日期。

## Solution

交付真实Google身份、组织授权、活动和链接投稿持久化的内部版本。业务金额仍不形成正式申请或付款义务。

**Success statement:** 下方阶段验收逐项有实际证据，三方看到一致且不越权的业务事实，未验证能力不会被当作可用。

**Appetite:** 代理规划时间盒：15个工作日；首个3个工作日检查最小登录/保存链路。不是创办人工期、报价或支出承诺；外部账号等待单列。到限报告剩余验收并重新切片，先削减次要筛选，不削权限和恢复。

## User Stories

1. As a 实施与运营负责人, I want 确认原型交接并建立可重复启动的内部环境，so that 让实施者从干净环境运行一个明确标示内部版本的页面，经业务入口读取数据库中的演示活动，并看到后台任务健康状态。
2. As a 商家、创作者或运营人员, I want 用户用Google登录后能安全刷新和退出，so that 用真实Google/Supabase测试配置登录内部版本，刷新仍识别本人，退出后服务端不再接受该会话的受保护写入。
3. As a 商家、创作者或运营人员, I want 同一用户能在本人和获授权商家组织间切换，so that 创作者创建自己的商家组织，已有成员按受控授权加入，并在各工作区看到正确数据。
4. As a 商家、创作者或运营人员, I want 用户换设备仍能恢复语言并继续表单，so that 首次询问、跳过、明确选择和账号偏好保存成为真实体验，切换语言不会丢失正在填写的活动或投稿。
5. As a 商家、创作者或运营人员, I want 商家保存规则草稿并明确知道为何不能真实发布，so that 商家保存活动资料、权利说明和规则，刷新或换浏览器继续编辑，并在预览中理解缺少的发布条件。
6. As a 商家、创作者或运营人员, I want 访客能分享公开活动并登录继续参与，so that 未登录访客在手机或电脑浏览公开fixture活动，看到演示标识与对应分享信息，登录后回到原活动继续参与。
7. As a 商家、创作者或运营人员, I want 创作者提交外部链接后能查回自己的投稿，so that 创作者查看明确模拟的账号资格并保存外部链接，之后可从另一浏览器查到同一投稿和待基线状态。
8. As a 商家、创作者或运营人员, I want 保存投稿后通知可靠到达且任务中断可恢复，so that 投稿保存后创作者收到持久站内回执，运营能看见通知失败原因并受控重试。
9. As a 商家、创作者或运营人员, I want 内部版本能在预发布环境恢复并保留已存数据，so that 团队在预发布版本完成登录、草稿和投稿保存，升级失败后恢复上一应用版本仍能继续。
10. As a 实施与运营负责人, I want 三端能重复完成真实保存内部版的交接验收，so that 交付可访问内部版本、启动说明和逐项证据，让M3使用真实身份/保存/任务基础而非浏览器演示账目。

## Implementation Decisions

1. 复用M1确认页面与设计系统，浏览器原型数据不迁入正式账目；M2范围是S0/S1及S2/S3保存。
2. Fastify为唯一业务和授权入口；Next.js仅页面、会话刷新及薄代理；Supabase仅Google与PostgreSQL，独立pg-boss worker。
3. 身份、活动、投稿按领域分界；组织及父对象组合约束在数据库落实，账号连接属于本人；运行角色不能修改不可变规则或直写受限业务表。
4. 保存变更携请求键和预期版本；冲突明确返回，不吞并其他人编辑。仅必要对象随纵向票建立迁移，不先建整套资金表。
5. 内测fixture活动与真实来源按环境及记录标签双重隔离；申请、审核确认、付款生产写入保持关闭，不能把原型状态直接落账。
6. 通知从同事务outbox进入单一持久任务路径；SSE仅失效提示，重读数据库为准，失败可轮询。

规则来源优先于历史草稿措辞：已批准默认和2026-09-15全栈方向为准；较早契约中“取整/付款阶段/跨活动仍待定”等历史句不重开已批准规则。本轮只细化执行和验收，不复制默认值、不修改源文件。具体实现文件位置在开工代码评审确定，本节不指定路径。

## Testing Decisions

- 最高可用边界为三端浏览器旅程→唯一业务API→真实PostgreSQL→受控提供方适配。优先复用现有M1页面测试和实际产品测试设施；当前仅核实原型规格/票据及设计系统文档存在，未核实产品仓库或测试代码，不能声称已有测试通过。
- 单元测试覆盖纯金额/期限规则，集成测试覆盖事务、权限、组织关系、重复键与任务恢复；Playwright覆盖用户可观察结果。fixture适配只替外部来源，不替数据库或服务器权限。测试名称含阶段AC，结果再映射PRD A及实施D。
- 测试边界由2026-09-16常规规划授权确定，不再额外问卷。只测外部行为和不变量，不测试内部实现形状；按每票风险增加故障/竞争/越权案例。
- 受影响范围完成类型/单元/集成检查，重型交付另有端到端与回退演练；保存独立跨厂商只读审阅。资金来源未知、真实权限未知和提供方准入不能由mock测试“通过”。
- 统一证据记录：验收ID、版本、环境、测试或人工步骤、期望、实际、时间、证据引用及未决项；当前全为未执行。发布候选必须区分模拟、沙盒及真实验证。

## Success Measures

记录登录成功/尝试次数、保存成功/尝试次数、换浏览器回读通过/检查次数、任务恢复延迟、越权被拒/攻击样本次数。必须标测试环境和样本量；以全部验收通过为内部退出条件，不填商业增长承诺。

## Out of Scope

真实社交OAuth/计量、正式奖励预留/审核/付款、生产发布、完整官网、视频上传、钱包及未来Whop商城。
